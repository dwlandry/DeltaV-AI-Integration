Hardware alarm condition parameters (Smart Switch)

Except for changing the value of the alarm level (ignore, maint, advise or fail) we strongly recommend that you do not adjust other default parameters in the switch module unless instructed to do so by Emerson to solve a specific issue.

A number of parameters hold information that determine how hardware alarm condition information in the switch is transformed into one of the PlantWeb-style hardware alarms.

For floating-point array parameters that hold information specific to a switch port (expressed as m.p where m = module number and p = port number in the module), the mapping of port m.p to port number (array index) n follows the rule:

Array index n = (switch module m - 1) * PPM + (switch module port p)

where PPM (Ports per Module):

  • Is 8 for FP20 and RM100 switches.
  • Is 4 for MD20 and MD30 switches.
  • Is 24 for RM104 switch

Thus for an RM100:

  • Port 1.1 information goes into HAC_XXXXXXXX_PRT[1]
  • (1 - 1) * 1 = 1
  • Port 4.8 information (if present) goes into HAC_XXXXXXXX_PRT[32]
  • (4 - 1) * 8 = 32

For an MD30:

  • Port 7.4 information (if present) goes into HAC_XXXXXXXX_PRT[28]
  • (7 - 1) * 4 = 28
For an RM104:
  • Port 1.1 information goes into HAC_XXXXXXXX_PRT[1]
  • (1 - 1) * 1 = 1
  • Port 1.24 information (if present) goes into HAC_XXXXXXXX_PRT[24]
  • (1 - 1) * 24 = 24

Information for installed ports is not necessarily contiguous in the array.

The parameter information that follows is arranged in the order the parameters appear in the switch module class function block diagram.

Switch Not Communicating

This condition is reported when the node hosting the switch module cannot communicate with the switch using the IP address in the MGMT_IP_ADDR parameter. Failure to communicate with the switch overrides all other switch conditions that may be configured causing them to become inactive:

  • It is not possible to configure the switch module to ignore the NOCOMM condition.
  • If there are any failures in reading information from the switch the raw NOCOMM condition is true.
  • On/off delay logic is applied using the values in HAC_NOCOMM_OND and HAC_NOCOMM_OFFD.

Switch Is Unlocked

If HAC_UNLOCKED_PWA.CVI has the value 1, 2, or 3 the workstation interrogates the switch for lockdown status and the time remaining on the lockdown timer

If the lockdown status is Unlocked and there is no time remaining on the lockdown timer the raw UNLOCKED condition is true.

On/off delay logic is applied using the values in HAC_UNLOCKED_OND and HAC_UNLOCKED_OFFD.

The result from the on/off delay logic is forced inactive if the current NOCOMM condition is active.

The result is reported as the UNLOCKED condition, visible in the Condition Summary application:

  • Subsystem: Switch
  • Message: DeltaV network switch unlocked
  • Alarm: Determined by value in HAC_UNLOCKED_PWA

Power Supply Unavailable

DeltaV Smart Switches support redundant power supply connections (and in the case of the RM100, an option for redundant power conversion electronics). Reporting the loss of one of the power sources allows repairs before both power sources fail.

If HAC_PSNAVAIL_PWA.CVI has the value 1, 2, or 3 the workstation interrogates the switch for the status of the power supply connections.

If either power supply connection is bad, the raw PSNAVAIL condition is true.

On/off delay logic is applied using the values in HAC_PSNAVAIL_OND and HAC_PSNAVAIL_OFFD.

The result from the on/off delay logic is forced inactive if the current NOCOMM condition is active.

The result is reported as the PSNAVAIL condtion, visible in the Condition Summary application:

  • Subsystem: Switch
  • Message: Power supply n unavailable (where n is either 1 or 2 to reflect the power supply that is unavailable).
  • Alarm: Determined by value in HAC_PSNAVAIL_PWA

When the switch power supply is not redundant you should either:

  • Make the (non-redundant) power connections to both Power supply 1 and Power supply 2, or
  • Configure HAC_PSNAVAIL_PWA as Ignore (0) to disable checking this condition.

Switch Chassis High Temperature

DeltaV Smart Switches can detect and report their chassis temperature. Operating above their rated temperature range can result in deteriorating switch behavior.

If HAC_HITEMP_PWA.CVI has the value 1, 2, or 3 the workstation interrogates the switch for its chassis temperature and writes the value to the HAC_HITEMP_VAL parameter.

If the value in HAC_HITEMP_VAL becomes greater than the value in HAC_HITEMP_LIM the raw HITEMP condition is true.

On/off delay logic is applied using the values in HAC_HITEMP_OND and HAC_HITEMP_OFFD.

The result from the on/off delay logic is forced inactive if the current NOCOMM condition is active.

The result is reported as the HITEMP condition, visible in the Condition Summary application:

  • Subsystem: Switch
  • Message: Switch temperature too high.
  • Alarm: Determined by value in HAC_HITEMP_PWA

If DeltaV Smart Switches with different temperature ranges are employed, adjust HAC_HITEMP_LIM as desired in each switch module.

If historical data on switch temperature is required, configure continuous history recording on HAC_HITEMP_VAL.

Switch Signal Relay Activated

You can use advanced switch management tools to configure the conditions that cause the signaling relay on the switch to activate. The signaling relay can then be used to drive local indication of the problems detected by the switch.

If HAC_SIGRACT_PWA.CVI has the value 1, 2, or 3 the workstation interrogates the switch for the status of the signal relay contacts. The value returned (1 = signal relay is activated; 2 = otherwise) is written to the HAC_SIGRACT_VAL parameter.

If HAC_SIGRACT_VAL has a value other than 2 the raw SIGRACT condition is true.

On/off delay logic is applied using the values in HAC_SIGRACT_OND and HAC_SIGRACT_OFFD.

The result from the on/off delay logic is forced inactive if the current NOCOMM HAC is active.

The result is reported as the SIGRACT condition visible in the Condition Summary application:

  • Subsystem: Switch
  • Message: Switch signal relay activated.
  • Alarm: Determined by value in HAC_SIGRACT_PWA

If historical data on the state of the signal relay is required, configure continuous history recording on HAC_SIGRACT_VAL.

Port Expected Communications Absent

When locking a DeltaV Smart Switch, ports that have been communicating remain enabled, and all other ports are disabled (do not permit communications while the switch is locked). Given the nature of communications between nodes on the DeltaV control network, regular communications is expected on all enabled ports on locked switches (including switch to switch communications.)

If HAC_COMABSNT_PWA.CVI has the value 1, 2, or 3 the workstation interrogates the switch for:

  • The list of all ports installed on the switch.
  • The switch lock status
  • Whether each port is enabled or disabled
  • Information about bytes received in the last 60 seconds on each installed port.

If the switch is locked each enabled port is examined. If there have been 0 bytes of (unblocked) data received from any device or switch connected to a port in the last 60 seconds the raw COMABSNT condition is true for that port.

On/off delay logic is applied using the values in HAC_COMABSNT_OND and HAC_COMABSNT_OFFD. The configurable on/off delay times are applied to all ports. Independent on/off delay timers used for each port.

The result from the on/off delay logic is forced inactive if the current NOCOMM condition is active.

The result is reported as the COMABSNT condition for that port, visible in the Condition Summary application:

  • Subsystem: Port
  • Message: Expected communications absent on port m.p.
  • Alarm: Determined by value in HAC_COMABSNT_PWA

Excessive Packets Discarded On Port

Unusually high levels of packets discarded (due to CRC errors, packets too small (runts) or packets too large (giants) can be an indicator of loose or deteriorating network cable connections, damaged network cables, or failing network interface electronics.

If HAC_DISCPKTS_PWA.CVI has the value 1, 2, or 3 the workstation interrogates the switch for:

  • The list of all ports installed on the switch.
  • Whether each port is enabled or disabled.
  • Information about packets discarded (due to CRC errors, runts, and giants) in the last 60 seconds on each installed port.

For each enabled port, the number of packets discarded in the last 60 seconds is written to the corresponding array element in HAC_DISCPKTS_PRT[n]. 0 is written for ports that are not installed or that are disabled.

The sum from all ports of the packets discarded in the last 60 seconds is written to HAC_DISCPKTS_VAL.

If the port is enabled, and if the number of discarded packets on this port in the last 60 seconds is greater than HAC_DISCPKTS_LIM the raw DISCPKTS condition is true for that port.

On/off delay logic is applied using the values in HAC_DISCPKTS_OND and HAC_DISCPKTS_OFFD. The configurable on/off delay times are applied to all ports. Independent on/off delay timers used for each port.

The result from the on/off delay logic is forced inactive if the current NOCOMM HAC is active.

The result is reported as the DISCPKTS condition for that port, visible in the Condition Summary application:

  • Subsystem: Port
  • Message: Excessive packets discarded on port m.p.
  • Alarm: Determined by value in HAC_DISCPKTS_PWA

If historical data on packet discard rates for this switch is desired, users should configure continuous history recording on HAC_DISCPKTS_VAL. Per port history could be captured by configuring history collection on individual elements of HAC_DISCPKTS_PRT[x].

High Link Utilization On Port

If HAC_HIUTIL_PWA.CVI has the value 1, 2, or 3 the workstation interrogates for:

  • The list of all ports installed on the switch.
  • Whether each port is enabled or disabled
  • Information about the link utilization in the last 30 seconds on each installed port.
Note: Link utilization information is for inbound communication on the ports. It does not include outbound communication.

For each enabled port, link utilization is written to the corresponding array element in HAC_HIUTIL_PRT[n]. 0 is written for ports that are disabled or not installed.

The maximum value from all elements of HAC_HIUTIL_PRT[n] elements is written to HAC_HIUTIL_VAL.

If the port is enabled and the link utilization on this port in the last 30 seconds is greater than HAC_HIUTIL_LIM the raw HIUTIL condition is true for that port.

Note: A common utilization limit as a percent of port speed is applied to all ports (connected to controllers, workstations and other switches), making the condition detection most sensitive to high traffic levels on ports connected to DeltaV workstations.

On/off delay logic is applied using the values in HAC_HIUTIL_OND and HAC_HIUTIL_OFFD. The configurable on/off delay times are applied to all ports. Independent on/off delay timers used for each port.

The result from the on/off delay logic is forced inactive if the current NOCOMM condition is active.

The result is reported as the HIUTIL condition for that port, visible in the Condition Summary application:

  • Subsystem: Port
  • Message: High link utilization on port m.p.
  • Alarm: Determined by value in HAC_HIUTIL_PWA

If historical data on link utilization for this switch is required, configure continuous history recording on HAC_HIUTIL_VAL. Per port history can be captured by configuring history collection on individual elements of HAC_HIUTIL_PRT[n].

Locking Violation On Port

When DeltaV Smart Switches are locked, ports with no communications activity are disabled. The other ports remain enabled, and the switch stores the MAC addresses of devices connected to these ports at the time the switch was locked. This is typically one MAC address for most ports and multiple MAC addresses for ports connected to other switches.

While locked, the switch communicates only with the device (MAC address) stored for each port, blocking communications with any other device (MAC address). When the switch detects (and blocks) communications with any device other than the one stored for that port, it is considered a port locking violation.

Switches also detect devices attempting to communicate on disabled ports. These are also considered port locking violations.

Port locking violations indicate attempts to attach an unauthorized device, or replace an expected device with an unauthorized device using the enabled port. Multiple port locking violations could indicate that network cables were disconnected and inadvertently reconnected to different ports on a locked switch.

If HAC_BLOCKING_PWA.CVI has the value 1, 2, or 3 the workstation interrogates the switch for:

  • The list of all ports installed on the switch.
  • The switch lock status.
  • Information about the presence of blocked communications in the last 60 seconds due to port locking (on enabled and disabled ports)

If the switch is locked and one or more packets received on the (enabled or disabled) port in the last 60 seconds were blocked due to port locking the raw BLOCKING condition is true for that port.

On/off delay logic is applied using the values in HAC_BLOCKING_OND and HAC_BLOCKING_OFFD. The configurable on/off delay times are applied to all ports. Independent on/off delay timers used for each port.

The result from the on/off delay logic is forced inactive if the current NOCOMM condition is active.

The result is reported as the BLOCKING condition for that port, visible in the Condition Summary application:

  • Subsystem: Port
  • Message: Port locking violation on port m.p.
  • Alarm: Determined by value in HAC_BLOCKING_PWA

In some cases, the removal of a violating device does not clear the information in the switch about the presence of the violating device.

The switch module periodically commands the switch to clear information about (old) violating devices if the switch module is configured to detect port violations (HAC_BLOCKING_PWA.CVI has the value 1, 2, or 3).

Switch Management Password

The HAC_MGINFO_* and HAC_MGINFOREM_* parameters are defined for the switch management password change reminder.

For all the following parameters:

  • The parameter category is either Configuration or Operating
  • Restore parameter value after restart is false (unchecked)
  • The "Allow named set changes for new instances" is false (unchecked), when applicable.
  • The parameter filter is either Common Configuration or Advanced Configuration
