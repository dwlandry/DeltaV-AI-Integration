Hardware alarm condition parameters (Smart Firewall)

*Except for changing the value of the alarm level (ignore, maint, advise or fail) it is strongly recommend that you do not adjust other default parameters in the firewall module unless instructed to do so by Emerson to solve a specific issue.

*A number of parameters hold information that determine how hardware alarm condition information in the firewall is transformed into one of the PlantWeb-style hardware alarms.

For all the following parameters:
  • The parameter category is either Configuration or Operating
  • Restore parameter value after restart is false (unchecked)
  • Allow named set changes for new instances is false (unchecked), when applicable
  • The parameter filter is one of Common Configuration, Advanced Configuration or On-line
The Smart Firewall has two ports; one port connects to the external LAN and another port connects to the DeltaV. The float array parameters used to hold information specific to a firewall port are size 2 arrays:
  • Index 1 for the port connecting to the external LAN
  • Index 2 for the port connecting to the DeltaV

The parameter information that follows is arranged in the order the parameters appear in the firewall module class function block diagram.

Firewall Not Communicating

This condition is reported when the node hosting the firewall module cannot communicate with the firewall using the IP address in the MGMT_IP_ADDR parameter. Failure to communicate with the firewall overrides all other firewall conditions that may be configured, causing them to become inactive:

  • It is not possible to configure the firewall module to ignore the NOCOMM condition.
  • If there are any failures in reading information from the firewall, the raw NOCOMM condition is true.
  • On/off delay logic is applied using the values in HAC_NOCOMM_OND and HAC_NOCOMM_OFFD.

Power Supply Unavailable

Emerson Smart Firewalls support redundant power supply connections. Reporting the loss of one of the power sources allows repairs before both power sources fail.

If HAC_PSNAVAIL_PWA.CVI has the value 1, 2, or 3 the workstation interrogates the firewall for the status of the power supply connections.

If either power supply connection is bad, the raw PSNAVAIL condition is true.

On/off delay logic is applied using the values in HAC_PSNAVAIL_OND and HAC_PSNAVAIL_OFFD.

The result from the on/off delay logic is forced inactive if the current NOCOMM condition is active.

The result is reported as the PSNAVAIL condtion, visible in the Condition Summary application:

  • Subsystem: Firewall
  • Message: Power supply n unavailable (where n is either 1 or 2 to reflect the power supply that is unavailable).
  • Alarm: Determined by value in HAC_PSNAVAIL_PWA

When the firewall power supply is not redundant you should either:

  • Make the (non-redundant) power connections to both Power supply 1 and Power supply 2, or
  • Configure HAC_PSNAVAIL_PWA as Ignore (0) to disable checking this condition.

Firewall Chassis High Temperature

Emerson Smart Firewalls can detect and report their chassis temperature. Operating above their rated temperature range can result in deteriorating firewall behavior.

If HAC_HITEMP_PWA.CVI has the value 1, 2, or 3 the workstation interrogates the firewall for its chassis temperature and writes the value to the HAC_HITEMP_VAL parameter.

If the value in HAC_HITEMP_VAL becomes greater than the value in HAC_HITEMP_LIM the raw HITEMP condition is true.

On/off delay logic is applied using the values in HAC_HITEMP_OND and HAC_HITEMP_OFFD.

The result from the on/off delay logic is forced inactive if the current NOCOMM condition is active.

The result is reported as the HITEMP condition, visible in the Condition Summary application:

  • Subsystem: Firewall
  • Message: Firewall temperature too high.
  • Alarm: Determined by value in HAC_HITEMP_PWA

If an Emerson Smart Firewall with a different temperature range is employed, adjust HAC_HITEMP_LIM as desired in the firewall.

If historical data on firewall temperature is required, configure continuous history recording on HAC_HITEMP_VAL.

Firewall Digital Signal Activated

You can use advanced firewall management tools to configure the conditions that cause the digital signal on the firewall to activate. The digital signal can then be used to drive local indication of the problems detected by the firewall.

If HAC_SIGACT_PWA.CVI has the value 1, 2, or 3 the workstation interrogates the firewall for the status of the digital signal contacts. The value returned (1 = digital signal is activated; 0 = otherwise) is written to the HAC_SIGACT_VAL parameter.

If HAC_SIGACT_VAL has a value other than 0 the raw SIGACT condition is true.

On/off delay logic is applied using the values in HAC_SIGACT_OND and HAC_SIGACT_OFFD.

The result from the on/off delay logic is forced inactive if the current NOCOMM HAC is active.

The result is reported as the SIGACT condition visible in the Condition Summary application:

  • Subsystem: Firewall
  • Message: Firewall digital signal activated.
  • Alarm: Determined by value in HAC_SIGACT_PWA

If historical data on the state of the digital signal is required, configure continuous history recording on HAC_SIGACT_VAL.

Excessive Packets Discarded On Port

Unusually high levels of packets discarded (due to CRC errors, packets too small (runts), or packets too large (giants) can be an indicator of loose or deteriorating network cable connections, damaged network cables, or failing network interface electronics.

If HAC_DISCPKTS_PWA.CVI has the value 1, 2, or 3, the workstation interrogates the firewall for:

  • The list of all ports installed on the firewall.
  • Whether each port is enabled or disabled.
  • Information about packets discarded (due to CRC errors, runts, and giants) in the last 60 seconds on each installed port.

For each enabled port, the number of packets discarded in the last 60 seconds is written to the corresponding array element in HAC_DISCPKTS_PRT[n]. 0 is written for ports that are not installed or that are disabled.

The sum from all ports of the packets discarded in the last 60 seconds is written to HAC_DISCPKTS_VAL.

If the port is enabled, and if the number of discarded packets on this port in the last 60 seconds is greater than HAC_DISCPKTS_LIM the raw DISCPKTS condition is true for that port.

On/off delay logic is applied using the values in HAC_DISCPKTS_OND and HAC_DISCPKTS_OFFD. The configurable on/off delay times are applied to all ports. Independent on/off delay timers used for each port.

The result from the on/off delay logic is forced inactive if the current NOCOMM HAC is active.

The result is reported as the DISCPKTS condition for that port, visible in the Condition Summary application:

  • Subsystem: Port
  • Message: Excessive packets discarded on port m.p.
  • Alarm: Determined by value in HAC_DISCPKTS_PWA

If historical data on packet discard rates for this firewall is desired, users should configure continuous history recording on HAC_DISCPKTS_VAL. Per port history could be captured by configuring history collection on individual elements of HAC_DISCPKTS_PRT[x].

High Link Utilization On Port

If HAC_HIUTIL_PWA.CVI has the value 1, 2, or 3 the workstation interrogates the firewall for:

  • The list of all ports installed on the firewall.
  • Whether each port is enabled or disabled
  • Information about the link utilization in the last 30 seconds on each installed port.
Note: Link utilization information is for inbound communication on the ports. It does not include outbound communication.

For each enabled port, link utilization is written to the corresponding array element in HAC_HIUTIL_PRT[n]. 0 is written for ports that are disabled or not installed.

The maximum value from all elements of HAC_HIUTIL_PRT[n] elements is written to HAC_HIUTIL_VAL.

If the port is enabled and the link utilization on this port in the last 30 seconds is greater than HAC_HIUTIL_LIM the raw HIUTIL condition is true for that port.

Note: A common utilization limit as a percent of port speed is applied to all ports (connected to controllers, workstations and other firewalls), making the condition detection most sensitive to high traffic levels on ports connected to DeltaV workstations.

On/off delay logic is applied using the values in HAC_HIUTIL_OND and HAC_HIUTIL_OFFD. The configurable on/off delay times are applied to all ports. Independent on/off delay timers are used for each port.

The result from the on/off delay logic is forced inactive if the current NOCOMM condition is active.

The result is reported as the HIUTIL condition for that port, visible in the Condition Summary application:

  • Subsystem: Port
  • Message: High link utilization on port m.p.
  • Alarm: Determined by value in HAC_HIUTIL_PWA

If historical data on link utilization for this firewall is required, configure continuous history recording on HAC_HIUTIL_VAL. Per port history can be captured by configuring history collection on individual elements of HAC_HIUTIL_PRT[n].
